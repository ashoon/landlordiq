## Project Purpose

**LandlordIQ** is a static single-page React application for a landlord managing 25+ rental units.
It provides two views:

1. **Units Dashboard** — a colour-coded grid of unit cards showing rent payment status
   (green = paid, amber = due soon, red = overdue) with a status filter bar and inline
   paid/unpaid toggle (persisted to `localStorage`).
2. **Financial Analytics** — KPI strip, rent expected-vs-collected bar chart, maintenance cost
   donut by category, and the maintenance expense / annual tax entry forms.

There is **no backend**. All data comes from JSON seed files; user data is stored in the browser and, optionally, mirrored
to a JSON file on the user's own Google Drive (see "Persistence & Google Drive sync").

## Data Model

### Units (tenant list) — stored data only, nothing built into the app

**No tenant details are in the source or the published build.** Tenants live only in store key `landlordiq_units`
(this device + the Google Drive file). Shape of `units`: `{ added: [unit], seeded: boolean }`, where a unit is:

```js
{
  id: string,           // "T01"–"T26" for the imported list, "N<timestamp>" for units added in the UI
  address: string,      // several tenants can share an address (e.g. "Calle 10", "Edificio Central")
  tenantName: string,
  phone: string,        // "" when unknown
  rentAmount: number,   // COP
  dueDay: number,       // day of month rent is due (clamped to the month's length)
  paidCurrentMonth: false
}
```

The starting list was moved to **`private/tenants.json`** (git-ignored; never commit it). `importSeedUnits()`
(`tenants.js`, called from `App.jsx`) copies it into stored data **once**, folding in older edits/deletions/added units,
then sets `seeded: true` and never runs again. It only works under `npm run dev` on a machine that has the file
(`seedUnits.js` uses `import.meta.glob` behind `import.meta.env.DEV`, so production builds contain no tenant data;
checked: no names or numbers in `dist/`). A published app or a new device starts with an empty list and gets its
tenants from Google Drive. With no units the dashboard shows an empty-state message.

There is no unit number: a "unit" is one tenant row, identified by `id`, shown by `address`. Lists sort by address
(natural order), then tenant name. No payment history is assumed: every month is **unpaid until marked paid**
(`setPaymentStatus`), so past months show as overdue until marked. The unit grid is sorted
overdue → due soon → upcoming → paid → vacant.

### Unit management

`Dashboard.jsx` renders `dashboard/ManageUnits.jsx` (collapsible table: edit address / tenant /
phone / rent / due day, add, delete; addresses may repeat). Units are read from store key `"landlordiq_units"`
by `getUnits()` in `tenants.js`.
Rent inputs step in 5,000 (`step="5000"`, `min="0"` so steps land on multiples of 5,000).
Helpers: `getEditableUnits`, `validateUnit`, `updateUnit`, `addUnit`, `deleteUnit`.

### Persistence & Google Drive sync

- **`src/data/store.js`** is the only module that touches `localStorage`. It keeps an in-memory cache
  (synchronous reads, write-through) of six data sets: `settings`, `units`, `tenancies`, `payments`, `expenses`, `taxes`
  (keys `landlordiq_<name>`). API: `getData`, `setData`, `exportAll`, `importAll` (validated), `fillData`,
  `isEmpty`, `subscribe(cb('local'|'remote'))`, `getMeta`/`setMeta`, `getBase`/`setBase` (last synced data, key
  `landlordiq_drive_base`, never uploaded), `saveLocalBackup`. Writes made by the app are
  `'local'`; imports and other-tab `storage` events are `'remote'`. `tenants.js` / `financials.js` use only this API.
- **`src/data/driveSync.js`** mirrors the store to `landlordiq-data.json` in Drive folder `Colombia/Apartments`
  (`FOLDER_PATH`; created on demand, existing root file moved on connect) when connected: Google Identity
  Services sign-in, scope `drive.file`, file discovered/created via the Drive v3 REST API. Local edits upload after a
  1.5 s debounce, serialized through a promise queue. Before each upload the file's content checksum (`md5Checksum`, falling back to `version`) is compared
  with the last synced one; a mismatch means someone else changed it, so `mergeWithRemote()` runs
  `mergeData(base, local, remote)` (`merge.js`: per-record/per-field three-way merge; deletions detected via the base;
  both changed the same field → local wins; edit beats remote deletion; no base → union), saves a local backup,
  imports the result and uploads it (retries up to 3 times if Drive moves again). Only when no base is stored does it
  raise status `conflict` (`resolveConflict('drive'|'mine')`; 'drive' keeps a local backup under `landlordiq_local_backup`).
  Every successful sync stores the agreed data via `markSynced(file, stamp, data)` → `setBase`. It polls every
  `POLL_INTERVAL_MS` (30 s) while the tab is visible and online, and also on tab focus / `online`; data is replaced only
  when the Drive checksum changed. Status states: `disabled | disconnected | connecting | synced | saving | unsynced |
  needs-auth | offline | conflict | error` (`getStatus`, `subscribeStatus`). Sync metadata (`landlordiq_drive_meta`:
  connected, fileId, version, dirty, lastSynced, shared, loginHint = Google email passed as `login_hint`) is never uploaded. After a refused silent sign-in (`needs-auth`) the next click anywhere runs `connect()` once (`armNextTapReconnect`). Without `VITE_GOOGLE_CLIENT_ID` the app is
  local-only.
- **Daily backup:** once a day `writeDailyBackup()` saves a copy of all data as `landlordiq-backup-YYYY-MM-DD.json` in the
  same Drive folder, and `pruneOldBackups()` permanently deletes backups older than `BACKUP_RETENTION_DAYS` (60). Both are best effort.
- **File picker (shared files):** `openSharedFile()` in `driveSync.js` opens Google's Picker (script `apis.google.com/js/api.js`,
  needs `VITE_GOOGLE_API_KEY`; `isPickerConfigured()` gates the UI buttons) so an account that was *shared* the data file
  can grant the app access to it (`drive.file`). It sets meta `{ fileId, shared: true, dirty: !isEmpty() }`, clears the
  base and runs `reconcile()`. Shared files are never moved into `Colombia/Apartments`, and if one disappears the app
  reports an error instead of creating a new file (`SHARED_GONE_MESSAGE`). `disconnect()` resets `shared`. The Picker needs
  the project number (`APP_ID` = client ID prefix) and the user's OAuth token. Untested with a real second account.
- **UI:** `layout/DriveStatus.jsx` (header chip: Connect / Reconnect / Save now / Disconnect) and
  `layout/SyncBanner.jsx` (conflict, expired sign-in, offline, error). `App.jsx` bumps `dataKey` on `'remote'`
  changes to remount the views.
- **Routing/hosting:** tabs use hash routing (`#/analytics`) and `vite.config.js` has `base: './'`, so the build
  works on GitHub Pages. `.github/workflows/deploy.yml` builds with the `GOOGLE_CLIENT_ID` repository variable.
  Setup steps are in `README.md`.
- Never add direct `localStorage` calls elsewhere; go through `store.js`.

### Tenant turnover (move out / move in)

Stored in store key `"landlordiq_tenancies"`: `{ [unitId]: Array<tenancy> }`, oldest first, created
only once a unit has a move-out. A tenancy = `{ tenantName, rentAmount, dueDay, moveIn, moveOut, payKey? }`;
it occupies the unit from `moveIn` up to (excluding) `moveOut`. Units without history have one implicit
open-ended tenancy built from the unit's own fields.

- **Rule:** whoever occupies the unit on its due date in a month owes that month's full rent. If nobody does,
  the row is `status: 'vacant'` (gray dashed card, sorts last, filter + summary count).
- Vacant units are excluded from `totalExpected`; their last rent is `vacancyLoss` (summary strip, KPI strip,
  gray "Vacancy Loss" bar). Analytics also shows `occupancyRate`.
- Actions in `ManageUnits.jsx` (data fns in `tenants.js`): `moveOutUnit`, `moveInUnit` (date may be in the
  future = scheduled), `undoMoveOut`, `cancelMoveIn`, with `validateMoveOut` / `validateMoveIn`.
- Payments of a replacement tenant are keyed by `payKey` so they never inherit the previous tenant's paid flag.

### Maintenance expenses

The old Monthly Costs table was removed; the analytics row is now the maintenance pie chart plus
`analytics/MaintenanceExpenses.jsx` (category, amount, optional note, per-entry delete). Entries are stored in
store key `"landlordiq_expenses"` (`[{ id, month: "YYYY-MM", category, amount, note }]`) and are the **only source** of
maintenance costs: `getFinancials()` totals them by category for each exact month (`addExpense`, `deleteExpense`,
`getExpenses`, `validateExpense`, `EXPENSE_CATEGORIES` in `financials.js`). Pie and KPIs therefore update.
Categories (in this order, General Repairs first/default): General Repairs, Plumbing, Electrical, Other (HVAC and Appliances were removed; old
entries in those categories are ignored). There are no sample costs; management fee and insurance no longer exist.
Each entry may also be linked to a unit: `unitId` plus the `address` it had when logged (both omitted when not linked). The
address shown/grouped is the unit's *current* address, falling back to the saved one if the unit was deleted
(`getExpenseAddress`). `getExpenseUnitOptions()` feeds the form's select (every option shows the address and the current tenant, or "Vacant").
`getMaintenanceByAddress(month)` totals the selected month and its calendar year per address, biggest yearly total first, with
unlinked expenses in one last row (`address: null`); `analytics/MaintenanceByAddress.jsx` shows it. Linking never changes the
pie chart or KPIs (those still total by category and month). Existing expenses stay unlinked.

### Annual property tax

`analytics/TaxPayments.jsx` records the tax, paid **once a year**: tax year, amount, date paid, optional note;
one payment per tax year (`validateTaxPayment`), stored in store key `"landlordiq_taxes"`
(`[{ id, year, amount, paidDate, note }]`). `getFinancials()` sets each month's `propertyTax` to the tax
paid in that calendar month (cash basis, `taxPaidIn`) — zero in all other months — so the payment month's NOI
absorbs the full amount. Helpers: `getTaxPayments`, `addTaxPayment`, `deleteTaxPayment`.

### Amount entry in COP mil

The expense and tax forms take amounts in **COP mil** (thousands): typing `450` stores 450000
(`milToAmount()` in `currency.js`). Lists show them as `COP 450 mil` (`formatCurrencyMil`). Data stored in
localStorage and JSON is always full pesos.

### Tracking start and next month

`src/data/tracking.js` stores `settings.trackingStart` ("YYYY-MM", store key `landlordiq_settings`), set to the
current month the first time the app runs (`ensureTrackingStart()` from `App.jsx`). It only **hides** older months:
nothing is ever deleted. The month picker (`getAvailableMonths()`) lists **next month** (some tenants pay before the
due date), the current month, then each month back to the start; the analytics chart never reaches before the start.
Marking a tenant paid in next month records the payment under that month, so it shows as paid when the month arrives.
`isEmpty()` ignores `settings` so a brand-new browser still adopts the Drive copy.

### Selected month

`App.jsx` owns `selectedMonth` (`"YYYY-MM"`, default current month), chosen via the `<select>` in
`Header.jsx` and passed to SummaryStrip, Dashboard and Analytics. `getAllTenants(month)`,
`getSummaryStats(month)` and `getFinancials(month)` (up to 6 months ending at the selection, never before the tracking start) all take it.
localStorage payment overrides (`landlordiq_payments`) are keyed `"<YYYY-MM>:<id>"` with value
`{ paid: boolean, paidDate: "YYYY-MM-DD" | null, dueDate?: "YYYY-MM-DD", payments?: [{ id, amount, date }], amountPaid?: number }`
(legacy boolean values still read; `amountPaid` is the older running-total form of part payments).
Marking paid stores today's date. On each card (`UnitCard.jsx`) the **Due** date (that month only, `setDueDate`) and, once
paid, the **Paid** date (`setPaidDate`) are plain text; clicking one turns it into a date field
(`dashboard/EditableDate.jsx`, calendar opens at once). A change saves on blur / Enter if it is a valid date
(`validateDate`); Escape cancels. Early and late payments are both allowed. Moving the due date back to the tenant's usual date removes
the override; marking unpaid clears the paid date and any part payment but keeps a changed due date.

### Part payments

"Mark as Paid" opens a panel on the card: **Paid in full**, or a **part payment** typed in COP mil (`recordPartialPayment`,
`validatePartPayment`, `describePayment` preview in `tenants.js`). Each part payment is saved as its own dated entry in the
override's `payments` list (`{ id, amount, date }`, date = today) and shown on the card as a list ("Oct 3, 2026 · COP 100,000").
Entries have ids so two devices adding payments at once both survive the Drive merge. An older total-only `amountPaid`
shows as one undated "Earlier" entry and is kept when a new payment is added. Amounts add up; an amount above the balance
is trimmed to it. When the total reaches the rent the month is marked paid, with the date of the last payment. Until then
the unit stays **unpaid** (status still follows the due date). `getAllTenants()` adds `paymentLog`, `amountPaid`,
`balance` and `daysCovered` to every row;
`daysCoveredBy()` = `floor(amountPaid × 30 / rent)` with `DAYS_PER_MONTH = 30` (never rounds up in the tenant's favour).
`getSummaryStats()` counts `amountPaid` in `totalCollected` and only the `balance` in the overdue / due-soon / upcoming
totals. Marking unpaid clears all part payments; marking paid in full keeps the list as history. Dashboard keeps the
tile in place after a part payment.

### Balance expected by, vacancy target and notes

- **Balance expected by:** a part payment can carry a date the rest is promised (`recordPartialPayment(..., balanceDueDate)`,
  or `setBalanceDueDate` to edit it). Stored as `balanceDue` on the payment override, exposed as `balanceDueDate` on the row
  (only while unpaid with at least one part payment). Information only: it turns red on the card once passed but never changes
  status, due date or totals. Marking paid/unpaid clears it; paying in full drops it.
- **Target move-in:** `units.added[].targetMoveIn` (`setTargetMoveIn`), editable on a vacant tile while no move-in is scheduled;
  cleared by `moveInUnit`. The vacant tile already shows days vacant (from the last move-out).
- **Notes:** `unitNote` lives on the unit (stays with the address), `tenantNote` on the tenancy (goes with the tenant). Both are
  edited in Manage Units and shown at the bottom of the tile (`tenantNote` not on vacant tiles).

### Cédula (tenant ID number)

Free-text `cedula` on the **tenancy** (set in Manage Units → Edit or Move in), so it belongs to the person living there and
the previous tenant's number stays in the history. It is shown only in the Manage Units table: not on unit tiles, not in the
dashboard search. No separate person record exists: a person who rents again is typed in again (a nullable `personId` was
deliberately not added; see the unit / tenancy / payments split above).

### Paid services (water, gas, electricity)

Three free-text fields on the unit record (`serviceWater`, `serviceGas`, `serviceElectricity`) for services the tenant pays
separately. They belong to the apartment, so they stay when tenants change (`updateUnit` always patches them onto the unit).
Edited in Manage Units → Edit (under the address), shown under the address in that table and at the bottom of the tile
(vacant tiles too). Contract renewals, contract ids and shared utility contract numbers are **not** built.

### Tenant insights (pays late / pays in parts)

`src/data/insights.js` works out, from payments already stored, how each tenant has paid. **Nothing new is stored** and it
never changes status, order, due dates or totals. `getTenantInsights(month)` (sorted: flagged first) and
`getTenantInsightMap(month)` (Map keyed `payKey ?? id`) read the last `WINDOW_MONTHS` (6) months ending at `month`
through `getAllTenants()`, never before the tracking start, and group by `payKey ?? id` so a replacement tenant has
their own record. Rules (constants `GRACE_DAYS` 7, `FLAG_THRESHOLD` 2):

- A month is **judged** once the rent is fully paid, or today is more than 7 days past its due date (edited due dates count).
- **Late**: full rent arrived more than 7 days after the due date, or is still not fully paid. A past month nobody
  marked therefore counts as late (accepted by the owner).
  A paid month always has a paid date; with part payments it is the date the last one completed the rent, so rent paid in
  several parts within 7 days of the due date is on time.
- **Part-payment month**: the rent was paid (or is being paid) in more than one payment, or one payment is recorded and a
  balance is still open. A single payment of the whole rent is not.
- **Pays late** = 2 or more late months; **Pays in parts** = 2 or more part-payment months.

Shown in `analytics/TenantInsights.jsx` (table for the selected month; **only flagged tenants are listed** until the "Show all tenants" button is pressed, `isFlagged()` in `insights.js`; `*` marks fewer than 6 judged months) and as a
violet **Watch** tag beside the status badge in `UnitCard.jsx` (reasons in its hover/aria text; never on vacant tiles).
`Dashboard.jsx` joins the map to the tiles. The badges use violet/sky so they are not mistaken for a payment status colour.

### Payment history by tenant

`src/data/paymentHistory.js` + `analytics/PaymentHistory.jsx` (bottom of the Analytics tab). Nothing new is stored: it reads every
tracked month through `getAllTenants()` and keeps the months where the chosen tenant owed rent. `getHistoryTenants()` lists
everyone who owed rent in a tracked month (current tenants first, former tenants marked "moved out"); a tenant is keyed
`payKey ?? id`, so a replacement tenant has their own history. `getPaymentHistory(key)` returns rows newest first (due date,
rent, paid, balance, dated payments, `daysFromDue` = paid date − due date once paid in full) and totals (months, total paid,
past-due balance, months paid after the due date). Next month is listed only if something was already paid for it. History
cannot reach before the tracking start (older data is hidden, not deleted); a month nobody marked paid shows as overdue.

### Languages (English / Spanish)

Two flag buttons in the header (`layout/LanguageSwitcher.jsx`) switch the whole app. `src/data/i18n.js` holds the
state: `t(englishText, params?)`, `getLanguage`, `setLanguage`, `subscribeLanguage`, `getLocale` ('en-US' / 'es-CO'),
`formatLocaleDate`, `formatToday`, `capitalize`. **The English text is the key**; `translations.es.js` maps it to
Spanish and a missing entry simply shows in English. `{name}` placeholders are filled from `params`. `App.jsx`
subscribes to the language so everything redraws. The choice is stored per device (`landlordiq_language`, via
`store.js`, **not** synced to Drive, so each person keeps their own); the first visit follows the browser language.
Dates, month names and number formats (`1.850.000` in Spanish) follow the language; money is still shown as `COP`.
Stored data (tenant names, notes, categories as saved) is never translated; expense categories are stored in English
and translated only for display. **New user-visible text must go through `t()` and get a Spanish entry.** Drive status
messages are English texts translated on display (`describeStatus`); Google's own error text is kept in `detail`.

### Attachments (contract scans, receipts)

Photos and PDFs can be attached to a **tenant's contract** (`ManageUnits.jsx`, button "Attach contract" under the tenant)
and to **maintenance expenses** and **annual tax payments** ("Attach receipt"). The Add Expense form also takes a receipt: the expense is saved first, then the file uploads, so a failed upload never loses the expense. One shared component,
`components/common/AttachmentList.jsx`, and one helper module, `src/data/attachments.js`, serve all three.

- **Files live on Google Drive, never in the synced JSON.** They are uploaded to `Colombia/Apartments/Contracts` or
  `Colombia/Apartments/Receipts` (`uploadAttachment`, `openAttachment`, `trashAttachment` at the end of `driveSync.js`;
  scope `drive.file` already covers files the app creates). The data only keeps a reference
  `{ id (Drive file id), name, mimeType, uploadedAt }` in an array: `contractFiles` on the **tenancy** (so it follows the
  tenant, not the apartment), `attachments` on an expense or tax payment. References carry an `id`, so `merge.js` needs no change.
- `attachments.js`: `validateAttachment` (photo or PDF, PDFs up to 10 MB), `uploadFile` (photos are shrunk client-side to
  1600 px JPEG first), `withAttachment` / `withoutAttachment`, `trashAttachments`. Data fns: `addContractFile`,
  `removeContractFile` (`tenants.js`); `addExpenseFile`, `removeExpenseFile`, `addTaxFile`, `removeTaxFile` (`financials.js`).
- Removing a reference, deleting an expense / tax payment / unit, or cancelling a scheduled move-in moves the Drive files to
  the trash (best effort, `trashAttachment`). Contract files stay with an ended tenancy as history.
- Uploading and opening need Drive connected and online (`isUploadAvailable()`); otherwise the button is disabled with a hint.
  Uploads are not queued. A file opens by downloading it through the API into a blob shown in a new tab.
- **Limits:** a second Google account that was shared the data file sees the references but cannot open the files
  (`drive.file` only grants access to files the app created for that account). The upload paths were not exercised against
  a real Drive account when written; only the data logic was checked.
- **Privacy:** contracts and cédulas are sensitive; they live only in the user's Drive and browser, never in git or the build.

### Look & feel (theme)

- **Font:** Inter (variable), bundled via `@fontsource-variable/inter` so it works offline. `text-xs` / `text-sm` are set one step larger
  in `tailwind.config.js` (13 px / 14.4 px); do not use `text-[11px]`-style sizes.
- **Colours are CSS variables** (`src/styles/index.css`, space-separated RGB) mapped in `tailwind.config.js`, so components use ordinary
  utilities and dark mode needs no `dark:` variants: the `.dark` class on `<html>` swaps the variables. Palette: slate `gray-*`
  neutrals, `brand-*` (deep blue-teal) as the one accent/primary colour, `bg-surface` for panels (white / dark navy).
  Use `bg-surface` instead of `bg-white`, and `bg-brand-600 text-white` for primary buttons (never `bg-gray-900 text-white`: gray flips in dark mode).
- **Status colours are unchanged**: `green-500`, `amber-400`, `red-500` keep Tailwind's values in both modes; only their tints/text
  shades (`*-50`, `*-100`, `*-600/700/800`) adapt for dark mode. Unit tiles use a thin border with a thick left edge in the status colour.
- **Dark mode:** `theme.js` (`getTheme`, `setTheme`, `subscribeTheme`, `getChartColors`), button in the header (`ThemeSwitcher.jsx`).
  Stored per device under `landlordiq_theme` via `store.js` (not synced to Drive); first visit follows the OS setting. Recharts needs real
  colour values, so charts read `getChartColors()` (App re-renders on theme change).
- Shared class strings live in `components/common/ui.js`; reuse them rather than copying input/button classes.
- Contrast was checked for both modes (body/secondary text 5.4:1 or better on tiles; hint text `gray-400` about 3.6:1 and used only for placeholders).

### Costs

There is no `financials.json`. Costs come only from user-entered data: maintenance expenses (by month) and annual
tax payments. Net operating income = rent collected − maintenance − property tax paid in that month.

## Key Conventions

- **No inline styles** — Tailwind utility classes only.
- **No hardcoded dates** — all date logic uses `new Date()`.
- **Status is computed, never stored** — `getStatusForTenant()` in `tenants.js` derives status at runtime.
- **Currency is COP** (Colombian peso). Full amounts go through `formatCurrency()` (`src/data/currency.js`, single `CURRENCY` constant). Large totals use "mil" (thousands): `formatMil()` (number only, KPI cards + chart axes with a "COP mil" caption) and `formatCurrencyMil()` ("COP 16,545 mil", summary strip). Seed rents are 380k–800k.
- **Store key** for payment overrides: `"landlordiq_payments"` (JSON object `{ ["YYYY-MM:id"]: { paid, paidDate } }`).
- **Due soon window**: unpaid and due within 3 days on a weekday, 4 days on Sat/Sun (`getDueSoonWindowDays()`); further out is `upcoming` (neutral gray). Grid order: overdue → due soon → upcoming → paid.
- **Status colours**: `paid` → green-500/green-50, `due-soon` → amber-400/amber-50, `overdue` → red-500/red-50.
- **Data transformations** live in `src/data/` only — never inside components.
- **New components** should include a JSDoc comment describing their props.

## State Architecture

```
App.jsx
  activeTab: 'dashboard' | 'analytics'     (useState)
  statsKey: number                          (incremented on unit toggle → re-renders SummaryStrip)

Dashboard.jsx
  filterStatus: 'all'|'paid'|'due-soon'|'overdue'  (useState)
  refreshKey: number                                 (incremented on toggle → forces re-read from tenants.js)

tenants.js (module)
  Reads the store (store.js) on every getAllTenants() call — no module-level caching of derived data
```
