## Project Purpose

**LandlordIQ** is a static single-page React application for a landlord managing 25+ rental units.
It provides two views:

1. **Units Dashboard** — a colour-coded grid of unit cards showing rent payment status
   (green = paid, amber = due soon, red = overdue) with a status filter bar and inline
   paid/unpaid toggle (persisted to `localStorage`).
2. **Financial Analytics** — KPI strip, rent expected-vs-collected bar chart, maintenance cost
   donut by category, and the maintenance expense / annual tax entry forms.

There is **no backend**. All data comes from JSON seed files; user data is stored in the browser and, optionally, mirrored
to a JSON file on the user's own Google Drive (see "Persistence & Google Drive sync").

## Data Model

### Units (tenant list) — stored data only, nothing built into the app

**No tenant details are in the source or the published build.** Tenants live only in store key `landlordiq_units`
(this device + the Google Drive file). Shape of `units`: `{ added: [unit], seeded: boolean }`, where a unit is:

```js
{
  id: string,           // "T01"–"T26" for the imported list, "N<timestamp>" for units added in the UI
  address: string,      // several tenants can share an address (e.g. "Calle 10", "Edificio Central")
  tenantName: string,
  phone: string,        // "" when unknown
  rentAmount: number,   // COP
  dueDay: number,       // day of month rent is due (clamped to the month's length)
  paidCurrentMonth: false
}
```

The starting list was moved to **`private/tenants.json`** (git-ignored; never commit it). `importSeedUnits()`
(`tenants.js`, called from `App.jsx`) copies it into stored data **once**, folding in older edits/deletions/added units,
then sets `seeded: true` and never runs again. It only works under `npm run dev` on a machine that has the file
(`seedUnits.js` uses `import.meta.glob` behind `import.meta.env.DEV`, so production builds contain no tenant data;
checked: no names or numbers in `dist/`). A published app or a new device starts with an empty list and gets its
tenants from Google Drive. With no units the dashboard shows an empty-state message.

There is no unit number: a "unit" is one tenant row, identified by `id`, shown by `address`. Lists sort by address
(natural order), then tenant name. No payment history is assumed: every month is **unpaid until marked paid**
(`setPaymentStatus`), so past months show as overdue until marked. The unit grid is sorted
overdue → due soon → upcoming → paid → vacant.

### Unit management

`Dashboard.jsx` renders `dashboard/ManageUnits.jsx` (collapsible table: edit address / tenant /
phone / rent / due day, add, delete; addresses may repeat). Units are read from store key `"landlordiq_units"`
by `getUnits()` in `tenants.js`.
Rent inputs step in 5,000 (`step="5000"`, `min="0"` so steps land on multiples of 5,000).
Helpers: `getEditableUnits`, `validateUnit`, `updateUnit`, `addUnit`, `deleteUnit`.

### Persistence & Google Drive sync

- **`src/data/store.js`** is the only module that touches `localStorage`. It keeps an in-memory cache
  (synchronous reads, write-through) of six data sets: `settings`, `units`, `tenancies`, `payments`, `expenses`, `taxes`
  (keys `landlordiq_<name>`). API: `getData`, `setData`, `exportAll`, `importAll` (validated), `fillData`,
  `isEmpty`, `subscribe(cb('local'|'remote'))`, `getMeta`/`setMeta`, `getBase`/`setBase` (last synced data, key
  `landlordiq_drive_base`, never uploaded), `saveLocalBackup`. Writes made by the app are
  `'local'`; imports and other-tab `storage` events are `'remote'`. `tenants.js` / `financials.js` use only this API.
- **`src/data/driveSync.js`** mirrors the store to `landlordiq-data.json` in Drive folder `Colombia/Apartments`
  (`FOLDER_PATH`; created on demand, existing root file moved on connect) when connected: Google Identity
  Services sign-in, scope `drive.file`, file discovered/created via the Drive v3 REST API. Local edits upload after a
  1.5 s debounce, serialized through a promise queue. Before each upload the file's content checksum (`md5Checksum`, falling back to `version`) is compared
  with the last synced one; a mismatch means someone else changed it, so `mergeWithRemote()` runs
  `mergeData(base, local, remote)` (`merge.js`: per-record/per-field three-way merge; deletions detected via the base;
  both changed the same field → local wins; edit beats remote deletion; no base → union), saves a local backup,
  imports the result and uploads it (retries up to 3 times if Drive moves again). Only when no base is stored does it
  raise status `conflict` (`resolveConflict('drive'|'mine')`; 'drive' keeps a local backup under `landlordiq_local_backup`).
  Every successful sync stores the agreed data via `markSynced(file, stamp, data)` → `setBase`. It polls every
  `POLL_INTERVAL_MS` (30 s) while the tab is visible and online, and also on tab focus / `online`; data is replaced only
  when the Drive checksum changed. Status states: `disabled | disconnected | connecting | synced | saving | unsynced |
  needs-auth | offline | conflict | error` (`getStatus`, `subscribeStatus`). Sync metadata (`landlordiq_drive_meta`:
  connected, fileId, version, dirty, lastSynced, shared) is never uploaded. Without `VITE_GOOGLE_CLIENT_ID` the app is
  local-only.
- **File picker (shared files):** `openSharedFile()` in `driveSync.js` opens Google's Picker (script `apis.google.com/js/api.js`,
  needs `VITE_GOOGLE_API_KEY`; `isPickerConfigured()` gates the UI buttons) so an account that was *shared* the data file
  can grant the app access to it (`drive.file`). It sets meta `{ fileId, shared: true, dirty: !isEmpty() }`, clears the
  base and runs `reconcile()`. Shared files are never moved into `Colombia/Apartments`, and if one disappears the app
  reports an error instead of creating a new file (`SHARED_GONE_MESSAGE`). `disconnect()` resets `shared`. The Picker needs
  the project number (`APP_ID` = client ID prefix) and the user's OAuth token. Untested with a real second account.
- **UI:** `layout/DriveStatus.jsx` (header chip: Connect / Reconnect / Save now / Disconnect) and
  `layout/SyncBanner.jsx` (conflict, expired sign-in, offline, error). `App.jsx` bumps `dataKey` on `'remote'`
  changes to remount the views.
- **Routing/hosting:** tabs use hash routing (`#/analytics`) and `vite.config.js` has `base: './'`, so the build
  works on GitHub Pages. `.github/workflows/deploy.yml` builds with the `GOOGLE_CLIENT_ID` repository variable.
  Setup steps are in `README.md`.
- Never add direct `localStorage` calls elsewhere; go through `store.js`.

### Tenant turnover (move out / move in)

Stored in store key `"landlordiq_tenancies"`: `{ [unitId]: Array<tenancy> }`, oldest first, created
only once a unit has a move-out. A tenancy = `{ tenantName, rentAmount, dueDay, moveIn, moveOut, payKey? }`;
it occupies the unit from `moveIn` up to (excluding) `moveOut`. Units without history have one implicit
open-ended tenancy built from the unit's own fields.

- **Rule:** whoever occupies the unit on its due date in a month owes that month's full rent. If nobody does,
  the row is `status: 'vacant'` (gray dashed card, sorts last, filter + summary count).
- Vacant units are excluded from `totalExpected`; their last rent is `vacancyLoss` (summary strip, KPI strip,
  gray "Vacancy Loss" bar). Analytics also shows `occupancyRate`.
- Actions in `ManageUnits.jsx` (data fns in `tenants.js`): `moveOutUnit`, `moveInUnit` (date may be in the
  future = scheduled), `undoMoveOut`, `cancelMoveIn`, with `validateMoveOut` / `validateMoveIn`.
- Payments of a replacement tenant are keyed by `payKey` so they never inherit the previous tenant's paid flag.

### Maintenance expenses

The old Monthly Costs table was removed; the analytics row is now the maintenance pie chart plus
`analytics/MaintenanceExpenses.jsx` (category, amount, optional note, per-entry delete). Entries are stored in
store key `"landlordiq_expenses"` (`[{ id, month: "YYYY-MM", category, amount, note }]`) and are the **only source** of
maintenance costs: `getFinancials()` totals them by category for each exact month (`addExpense`, `deleteExpense`,
`getExpenses`, `validateExpense`, `EXPENSE_CATEGORIES` in `financials.js`). Pie and KPIs therefore update.
Categories (in this order, General Repairs first/default): General Repairs, Plumbing, Electrical, Other (HVAC and Appliances were removed; old
entries in those categories are ignored). There are no sample costs; management fee and insurance no longer exist.

### Annual property tax

`analytics/TaxPayments.jsx` records the tax, paid **once a year**: tax year, amount, date paid, optional note;
one payment per tax year (`validateTaxPayment`), stored in store key `"landlordiq_taxes"`
(`[{ id, year, amount, paidDate, note }]`). `getFinancials()` sets each month's `propertyTax` to the tax
paid in that calendar month (cash basis, `taxPaidIn`) — zero in all other months — so the payment month's NOI
absorbs the full amount. Helpers: `getTaxPayments`, `addTaxPayment`, `deleteTaxPayment`.

### Amount entry in COP mil

The expense and tax forms take amounts in **COP mil** (thousands): typing `450` stores 450000
(`milToAmount()` in `currency.js`). Lists show them as `COP 450 mil` (`formatCurrencyMil`). Data stored in
localStorage and JSON is always full pesos.

### Tracking start and next month

`src/data/tracking.js` stores `settings.trackingStart` ("YYYY-MM", store key `landlordiq_settings`), set to the
current month the first time the app runs (`ensureTrackingStart()` from `App.jsx`). It only **hides** older months:
nothing is ever deleted. The month picker (`getAvailableMonths()`) lists **next month** (some tenants pay before the
due date), the current month, then each month back to the start; the analytics chart never reaches before the start.
Marking a tenant paid in next month records the payment under that month, so it shows as paid when the month arrives.
`isEmpty()` ignores `settings` so a brand-new browser still adopts the Drive copy.

### Selected month

`App.jsx` owns `selectedMonth` (`"YYYY-MM"`, default current month), chosen via the `<select>` in
`Header.jsx` and passed to SummaryStrip, Dashboard and Analytics. `getAllTenants(month)`,
`getSummaryStats(month)` and `getFinancials(month)` (up to 6 months ending at the selection, never before the tracking start) all take it.
localStorage payment overrides (`landlordiq_payments`) are keyed `"<YYYY-MM>:<id>"` with value
`{ paid: boolean, paidDate: "YYYY-MM-DD" | null, dueDate?: "YYYY-MM-DD", amountPaid?: number }` (legacy boolean values still read).
Marking paid stores today's date. On each card (`UnitCard.jsx`) the **Due** date (that month only, `setDueDate`) and, once
paid, the **Paid** date (`setPaidDate`) are plain text; clicking one turns it into a date field
(`dashboard/EditableDate.jsx`, calendar opens at once). A change saves on blur / Enter if it is a valid date
(`validateDate`); Escape cancels. Early and late payments are both allowed. Moving the due date back to the tenant's usual date removes
the override; marking unpaid clears the paid date and any part payment but keeps a changed due date.

### Part payments

"Mark as Paid" opens a panel on the card: **Paid in full**, or a **part payment** typed in COP mil (`recordPartialPayment`,
`validatePartPayment`, `describePayment` preview in `tenants.js`). Amounts add up; when the total reaches the rent the month
is marked paid (today's date). Until then the unit stays **unpaid** (status still follows the due date) and the override
carries `amountPaid`. `getAllTenants()` adds `amountPaid`, `balance` and `daysCovered` to every row;
`daysCoveredBy()` = `floor(amountPaid × 30 / rent)` with `DAYS_PER_MONTH = 30` (never rounds up in the tenant's favour).
`getSummaryStats()` counts `amountPaid` in `totalCollected` and only the `balance` in the overdue / due-soon / upcoming
totals. Marking unpaid clears the part payment. Dashboard keeps the tile in place after a part payment.

### Costs

There is no `financials.json`. Costs come only from user-entered data: maintenance expenses (by month) and annual
tax payments. Net operating income = rent collected − maintenance − property tax paid in that month.

## Key Conventions

- **No inline styles** — Tailwind utility classes only.
- **No hardcoded dates** — all date logic uses `new Date()`.
- **Status is computed, never stored** — `getStatusForTenant()` in `tenants.js` derives status at runtime.
- **Currency is COP** (Colombian peso). Full amounts go through `formatCurrency()` (`src/data/currency.js`, single `CURRENCY` constant). Large totals use "mil" (thousands): `formatMil()` (number only, KPI cards + chart axes with a "COP mil" caption) and `formatCurrencyMil()` ("COP 16,545 mil", summary strip). Seed rents are 380k–800k.
- **Store key** for payment overrides: `"landlordiq_payments"` (JSON object `{ ["YYYY-MM:id"]: { paid, paidDate } }`).
- **Due soon window**: unpaid and due within 3 days on a weekday, 4 days on Sat/Sun (`getDueSoonWindowDays()`); further out is `upcoming` (neutral gray). Grid order: overdue → due soon → upcoming → paid.
- **Status colours**: `paid` → green-500/green-50, `due-soon` → amber-400/amber-50, `overdue` → red-500/red-50.
- **Data transformations** live in `src/data/` only — never inside components.
- **New components** should include a JSDoc comment describing their props.

## State Architecture

```
App.jsx
  activeTab: 'dashboard' | 'analytics'     (useState)
  statsKey: number                          (incremented on unit toggle → re-renders SummaryStrip)

Dashboard.jsx
  filterStatus: 'all'|'paid'|'due-soon'|'overdue'  (useState)
  refreshKey: number                                 (incremented on toggle → forces re-read from tenants.js)

tenants.js (module)
  Reads the store (store.js) on every getAllTenants() call — no module-level caching of derived data
```
